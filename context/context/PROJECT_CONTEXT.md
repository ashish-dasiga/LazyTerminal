# Lazy Terminal — Agreed Project Context

## Product definition
Lazy Terminal is a mobile-first, local-first development companion. The Android app controls a Windows PC companion so a developer can browse/edit files, use a real terminal, launch supported AI coding agents, manage Git, run development tasks, and preview supported project output from a phone.

## Deliverables
1. Android APK: mobile UI, pairing, terminal interaction, file/project navigation, local offline queue and reconciliation.
2. Windows EXE: companion/host process, pairing secret generation, approved filesystem access, shell/process execution, Git and CLI adapters, state synchronization.

## Frontend is the source of truth
`source-frontend/` is the exact supplied frontend source. Preserve its visual design, layout, navigation, colors, typography, logo/branding, responsive behavior and existing screens. Build real functionality behind the existing UI through its service-contract/adapter boundary. Do not redesign or replace it. Any visual change requires explicit owner approval.

The frontend contains React 19, TypeScript, Vite, Tailwind CSS and Lucide icons. It includes mobile and Windows-host views, terminal, Explorer/editor, Source Control, Run/Debug, Preview, CLI Manager, Settings, More, Pairing, Projects, Offline Queue, reconciliation UI, and mock services. The source frontend ZIP contains no separate standalone logo image; the specification kit includes the workflow asset under `assets/`.

## Confirmed behavior
- PC-dependent commands, file operations, Git operations, CLI agents and preview servers execute on the PC.
- When the PC is offline, the mobile app remains usable for locally saved drafts/eligible queued tasks and cached last-synced information. It must not pretend PC work executed.
- On reconnection, synchronize state, mark stale information appropriately, validate/reconcile queued tasks, show the user what will happen, and require explicit approval before execution.
- Offline queueing is not execution.
- The PC is the source of truth for live PC files, shell sessions and agent processes.
- A fresh random pairing secret is generated by the PC companion at each communication-service startup. Pairing must not rely on a permanent hard-coded key.
- No localhost browser dashboard is the product.
- No mandatory paid cloud, database, API or relay. Target mandatory running cost is ₹0.
- Cloud execution is explicitly deferred until the local-first product is stable. Do not build cloud workers, cloud mode, or cloud billing in current phases except to keep an architecture boundary clean.
- LAN-first connectivity is acceptable for the initial MVP. Do not promise remote internet connectivity until designed and tested.
- Android APK and Windows EXE packaging are required; a Vite web page alone is not a final deliverable.

## Implementation status
The specification and frontend exist, but that does not mean the native APK, Windows companion, transport, or end-to-end behavior already exists. Audit before assuming implementation. Existing mock behavior must be identified and replaced or clearly retained only for tests/demo.
